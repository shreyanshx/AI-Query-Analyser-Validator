# SQL Analyzer & Validator — raw-EC2 React + FastAPI MVP (v1)

The change set is the entire platform: a FastAPI backend (Cognito JWT auth, read-only DB schema introspection with a per-user TTL cache, a SQLGlot-based deterministic validator and rule-based optimizer, and a four-provider AI fallback chain), a Vite React+TS SPA (Cognito auth flows, connection manager, analyzer workspace, schema tree), and raw-EC2 deployment assets (Nginx, systemd/Gunicorn, bootstrap). It is built against the architecture steering doc and the hard hosting/auth/safety requirements. The two safety invariants that matter most — never execute user or AI SQL, and never leak DB passwords or provider keys to logs/responses/browser — hold across every path I traced: the DB adapter runs only parameterized `information_schema`/`pg_catalog` reads, the validator/optimizer are pure AST analysis, every AI suggestion is re-validated by the deterministic validator before being marked valid, and credentials are `SecretStr`/redacted/IAM-sourced. The AI fallback trigger discipline (fall back on unavailable, stop on refusal) is correctly encoded and well tested.

Watch for: (1) **confirmed** — Cognito client-id/audience enforcement is silently skipped whenever `COGNITO_APP_CLIENT_ID` is unset, and issuer verification is skipped when the pool id is unset, so a misconfigured deploy fails open to accepting any Cognito-signed token; (2) **confirmed** — only the Postgres adapter exists, so the "multiple dialects" DB-connection requirement is a parse-time-only capability (MySQL/SQL Server/etc. connections raise `NotImplementedError`); (3) **likely** — the production CORS/`CORS_ORIGINS` default ships as `http://localhost:5173` and must be overridden per-env or protected routes will reject the real SPA origin. None of these are safety-invariant breaches; (1) is the one worth gating on.

**Verdict**: NEEDS_CHANGES

## High-level view

The safety model is the strongest part of the implementation. There is no code path from an API request to query execution: `DBAdapter` exposes only `test_connection`, `introspect_schema`, and an opt-in `sample_column`, all built from parameterized catalog reads, and the validator/optimizer operate purely on the SQLGlot AST. User SQL and AI SQL are only ever parsed, never run, and `sample_column` is additionally gated behind a global flag, a per-request opt-in, and a sensitive-column denylist — though no route currently exposes it.

Credential handling is consistent with the spec. DB passwords are `SecretStr`, never serialized back (verified by tests scanning response bodies), and reach only psycopg. AI keys are read from settings/Secrets Manager, sent only in the provider request, and asserted absent from the normalized suggestion. Bedrock uses the boto3 default chain (EC2 IAM role), no static key. A redaction logging filter scrubs passwords, connection strings, bearer tokens, and known key names, and the code consistently logs identifiers (`user.sub`) rather than config.

Cognito JWT validation is real (signature via JWKS with kid lookup and one rotation retry, issuer, exp, token_use, and access-token client_id), and the frontend/backend agree on using the access token. The gap is that audience/client_id and issuer checks are conditional on the corresponding settings being non-empty, so a deploy that forgets to set `COGNITO_APP_CLIENT_ID` or `COGNITO_USER_POOL_ID` degrades to accepting any token Cognito signed, with no startup guard to catch it.

The AI layer is the cleanest subsystem: a single normalized `AISuggestion` shape, an exception taxonomy that encodes the fallback rule (`ProviderUnavailable` → next provider; `ProviderRefusal`/`ProviderError` → stop), per-provider mapping of 429/5xx/timeout/throttle to "unavailable" and safety refusals to "refusal", and mandatory deterministic re-validation of every suggestion in the optimize route. All of this is exercised by substantive tests.

The deployment and dialect story has the real functional gaps. The DB layer only implements Postgres; every other dialect is a parse-time capability only. Deployment assets match the raw-EC2/Nginx/systemd/ALB-terminates-TLS requirement, but ship with placeholder config (`CORS_ORIGINS` localhost default, `REPLACE_ME_ORG` repo URL) that must be set per environment.

### No execution path for user or AI SQL

`DBAdapter` declares only `test_connection`, `introspect_schema`, and `sample_column`; there is no generic `execute`. The one path that reads row data — `sample_column` — first checks the identifier exists in `information_schema.columns` with bound parameters, then builds the query with `psycopg.sql.Identifier` quoting rather than string interpolation, so it cannot be driven by attacker-chosen SQL. AI-generated SQL is treated as untrusted text: `_ai_optimize` runs the model's `suggested_sql` back through `SqlValidator.validate` against the same cached schema and sets `is_suggestion_valid` from that result; an invalid suggestion is still shown but badged "not validated" (`test_optimize_ai_bad_sql_is_revalidated_false`). The frontend only renders the suggested SQL with copy/export buttons — nothing executes it.

### Credential confinement: SecretStr, redaction, IAM

DB passwords are `SecretStr` on `ConnectionConfig` and only unwrapped inside `PostgresAdapter._connect` via `get_secret_value()`. `ConnectionInfo` (the client-facing shape) has no password field, and `fingerprint()` deliberately excludes it. Two tests scan the full response text for `super-secret-pw` and the literal `password` to prove nothing leaks.

AI keys live in settings (sourced from Secrets Manager at startup) and are sent only in the provider HTTP request — Gemini via query param, OpenAI via bearer header, Anthropic via `x-api-key`; the provider tests assert the key is present on the wire and absent from `suggestion.model_dump_json()`. Bedrock uses the boto3 default credential chain with no static key, matching the "Bedrock via EC2 IAM role" requirement. `AISuggestion` carries no credential field. The redaction filter in `logging_utils` covers `key=value`/JSON forms of sensitive keys, `scheme://user:password@` connection strings, and `Bearer <token>`; code paths log `user.sub` and provider names, not config values.

One residual to note rather than block: the schema summary sent to the AI provider is built only from structural metadata (`summarize_schema` emits table/column/type/index names), and `PromptContext` has no field for row values or credentials, so the "never send DB credentials/sampled values to the provider" rule is structurally enforced, not merely by convention.

### Cognito JWT validation is sound but fails open on missing config

`CognitoVerifier.verify_token` does the real work: it reads the `kid` from the token header, looks up the matching JWKS key (refreshing the cache once to tolerate key rotation), and calls `jwt.decode` with `algorithms=["RS256"]`, the derived issuer, and — for id tokens — the app client id as audience. It then checks `token_use` matches the expected value, checks `client_id` against the app client for access tokens, and requires a `sub`. Signature, exp (python-jose enforces by default; `test_expired_token_is_401` confirms), issuer, token_use, and client/audience are all covered, and the frontend sends the access token that the `access` default expects.

The gap is conditional enforcement:

```python
decode_kwargs = {"algorithms": ["RS256"], "issuer": settings.COGNITO_ISSUER or None}
if token_use_expected == "id" and settings.COGNITO_APP_CLIENT_ID:
    decode_kwargs["audience"] = settings.COGNITO_APP_CLIENT_ID
else:
    decode_kwargs["options"] = {"verify_aud": False}
...
if token_use_expected == "access" and settings.COGNITO_APP_CLIENT_ID:
    if claims.get("client_id") != settings.COGNITO_APP_CLIENT_ID:
        raise AuthError(...)
```

If `COGNITO_APP_CLIENT_ID` is empty, the client_id/audience binding is skipped entirely for both token modes, and `COGNITO_ISSUER` is empty (hence `issuer=None`, disabling issuer verification) whenever `COGNITO_USER_POOL_ID` is empty. The net effect of a half-configured deploy is that any token signed by *some* Cognito pool whose JWKS the verifier can fetch would pass — the audience that scopes a token to *this* app is no longer enforced. Nothing fails loudly at startup. A config guard that refuses to start (or 500s protected routes) unless pool id and client id are both set would turn a silent auth weakening into an obvious boot failure.

### AI fallback chain and the refusal/unavailable distinction

The exception hierarchy is the mechanism: `ProviderUnavailable` is the only exception the orchestrator catches to continue the loop; `ProviderRefusal` and `ProviderError` propagate and stop the chain. Each provider maps transport conditions correctly — 429 and ≥500 and timeouts/transport errors → `ProviderUnavailable`; other 4xx → `ProviderError`; explicit safety signals (`finishReason==SAFETY`/`promptFeedback.blockReason`, `finish_reason==content_filter`, `stop_reason==refusal`) → `ProviderRefusal`. Bedrock additionally maps throttling/server/model-not-ready codes to unavailable and `AccessDeniedException` to a non-fallback `ProviderError` (a deliberate deny, correctly not routed around). `test_refusal_does_not_fall_back` proves the second provider is never called on a refusal, and `test_all_unavailable_raises`/`test_none_configured_raises` cover the degrade path.

The optimize route turns `AllProvidersUnavailable` and `ProviderRefusal` into `ai_available=false` with distinct messages while preserving the deterministic result, so "all providers down → syntax+schema validation still works, UI shows AI unavailable" is satisfied (`test_optimize_ai_unavailable_does_not_block_rule_based`, and the frontend renders the "AI temporarily unavailable" notice). Minor cosmetic: the orchestrator logs "falling back" even when the failing provider is the last one in the chain — harmless but slightly misleading in logs.

### Validator and optimizer: all statement types, estimates only

The validator parses with the dialect-mapped SQLGlot reader and classifies each statement, and the parametrized test covers SELECT/INSERT/UPDATE/DELETE/CREATE/CTE/multi-statement — satisfying "validate all supported statement types, not only SELECT." Schema-aware validation resolves CTE names and table/subquery aliases as local scopes (so they are never reported as unknown tables), flags unknown real tables and unknown qualified/unqualified columns, and demotes ambiguous/unqualified multi-table columns to warnings. The optimizer is a set of independent pure rules (SELECT \*, missing WHERE on UPDATE/DELETE, index suggestions, leading-wildcard LIKE, non-sargable function wraps, missing join condition, unbounded SELECT) and every message and the `performance_note` is explicitly framed as an estimate, honoring the "estimates unless EXPLAIN enabled" rule (`EXPLAIN_ENABLED` exists as a flag; no execution path consumes it yet, which is consistent with the MVP).

One edge worth a targeted test: `validate_against_schema` applies its unqualified-column logic uniformly across statement types via `find_all(exp.Column)`. For INSERT column lists or CREATE TABLE definitions this could in principle surface spurious "Unknown column" results depending on how SQLGlot models those columns against the single statement's table set. The valid-statement test only checks *syntax* for INSERT/CREATE, not schema validation, so this corner is unverified.

### Dialects: parse-time breadth, Postgres-only connectivity

`normalize_dialect` maps a healthy set of dialect aliases to SQLGlot identifiers, so syntax validation genuinely spans multiple dialects. But `create_adapter` only returns a `PostgresAdapter`; MySQL/SQL Server/SQLite/Oracle are explicit `NotImplementedError` placeholders. So schema-aware validation, connection testing, and sampling — anything requiring a live DB — work for Postgres only. This is a reasonable MVP scope but it narrows the "multiple dialects" requirement to syntax validation; it should be stated as a known limitation rather than left implicit, since the UI offers all dialects in its dropdown.

### Deployment matches the raw-EC2 constraint

The topology matches the requirement: Nginx serves the static React build and reverse-proxies `/api/` + `/health` to `127.0.0.1:8000` on port 80 only (TLS at the ALB), systemd runs Gunicorn+Uvicorn as non-root `aiqav` with hardening flags and an uncommitted `EnvironmentFile`, bootstrap.sh seeds `backend.env` `chmod 600` from the non-VITE keys of `.env.example`, and no Docker/ECS/S3/CloudFront appears anywhere. The placeholders that must be set before a real deploy are `REPO_URL` (`REPLACE_ME_ORG`) and — the ones that affect correctness — `CORS_ORIGINS` (defaults to localhost) and the Cognito ids discussed above.

### Tests exercise real logic

The suite is not trivial-assertion padding. Auth tests sign real RS256 tokens with a locally generated RSA keypair and inject the matching JWKS, so signature verification, expiry, and the 401 paths are genuinely exercised. Provider tests mock HTTP with respx and stub the boto3 Bedrock client, asserting both the success parse and that the key is on the wire but absent from the suggestion, plus the 429→unavailable / 400→error / throttle→unavailable / access-denied→error mappings. Orchestrator tests prove fallback-on-unavailable, stop-on-refusal, skip-unconfigured, and all-down behaviors, and the optimize integration tests prove AI re-validation (valid and invalid) and best-effort non-blocking. The main untested corner is the INSERT/CREATE schema-validation edge noted above, and the config-dependent JWT fail-open (there is no test asserting behavior when client id/issuer are unset).
