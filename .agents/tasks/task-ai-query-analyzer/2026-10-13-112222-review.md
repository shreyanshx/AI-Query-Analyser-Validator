# SQL Analyzer & Validator — fail-closed Cognito gating and v1 review fixes (v2)

This pass re-reviews commit `38f0101`, which addresses the six issues raised in v1. The headline fix is the JWT fail-open: a half-configured deployment now fails *closed* — `verify_token` refuses outright and `get_current_user` returns 503 unless both the Cognito user pool id and app client id are set, and when configured, issuer and audience/client_id are enforced unconditionally for both access and id token modes. The CREATE/INSERT false-positive in the schema validator was real and is now fixed with a tightly-scoped carve-out that still validates CTAS sources and CREATE INDEX targets. The remaining items (Postgres-only live-DB support, the localhost CORS default, the stale optimize docstring) are resolved by documentation, a startup warning, and a one-line docstring edit respectively. All fixes are backed by new tests, and no regression was introduced in the paths I traced; the safety invariants from v1 still hold.

Watch for: nothing blocking. One **possible** residual worth noting but not gating on — the 503 on an unconfigured deployment is returned before the credential-presence check, so unauthenticated callers can distinguish "auth not configured" from "token missing"; this is an intentional operability trade-off documented in the code and is not an auth weakening.

**Verdict**: APPROVED

## High-level view

The gating fix resolves issues #1 and #5 at their shared root cause. `Settings.cognito_fully_configured` requires both the pool id and the client id; `verify_token` raises before any decode when that is false, and `get_current_user` short-circuits to 503. With both guaranteed non-empty, the branches that previously skipped audience/client_id and disabled issuer verification are gone, so those checks are unconditional for access *and* id tokens.

The validator carve-out for CREATE is keyed to the single created name only: a `CREATE TABLE`/`VIEW` target and its declared columns become a local scope, but `CREATE TABLE ... AS SELECT` still validates source tables and `CREATE INDEX ... ON existing_table` still validates its target. The v1 "possible" concern was a genuine false positive, now fixed and pinned by five targeted tests.

Postgres-only live-DB support is now an explicit MVP limitation in the README and surfaced in the SPA for non-Postgres dialects. The localhost CORS default is kept for dev but flagged as production-critical in `.env.example` and backed by a startup warning. The stale "once FEAT-003 lands" docstring is corrected.

### Cognito gating now fails closed

v1's weakness was that audience/client_id enforcement and issuer verification were each gated on their settings being non-empty, so a deploy that forgot `COGNITO_APP_CLIENT_ID` or `COGNITO_USER_POOL_ID` degraded to accepting any Cognito-signed token. The new `cognito_fully_configured` property requires both, and two independent layers enforce it: `verify_token` raises `AuthError` before fetching a JWKS key or decoding anything, and `get_current_user` raises 503 at the dependency boundary. Because the guard guarantees both values are present on every path that reaches the decode, the previously-conditional branches collapse to unconditional checks:

```python
decode_kwargs = {"algorithms": ["RS256"], "issuer": settings.COGNITO_ISSUER}
if token_use_expected == "id":
    decode_kwargs["audience"] = settings.COGNITO_APP_CLIENT_ID
else:
    decode_kwargs["options"] = {"verify_aud": False}  # client_id checked from claims below
...
if token_use_expected == "access":
    if claims.get("client_id") != settings.COGNITO_APP_CLIENT_ID:
        raise AuthError("Token client_id does not match app client")
```

Issuer is no longer `... or None` (which disabled the check), id-token mode always binds `aud` to the app client, and access-token mode always enforces `client_id` from the claims. Signature, exp, token_use, issuer, and audience/client_id are therefore all enforced whenever the service will serve a request. This resolves issues #1 and #5.

Enforcement at the verifier (not only the dependency) matters because a future caller invoking the verifier outside the FastAPI dependency still fails closed. The test suite pins both layers — HTTP-level 503 for missing client_id, missing pool_id, and id-token mode; a verifier-level `AuthError` for both token modes; and a fully-configured regression test that a valid token still returns 200.

One residual, non-blocking: in `get_current_user` the `cognito_fully_configured` 503 is raised before the `credentials is None` 401. An unauthenticated caller can therefore distinguish a misconfigured deployment from a missing token. This exposes deployment config state (not user data) and is a reasonable operability trade-off — the 503 is explicitly chosen so the operational cause is unambiguous. Flagged only so a future reviewer who wants a stricter posture knows the ordering is intentional.

### CREATE/INSERT schema-validation carve-out

The v1 "possible" concern turned out to be a real false positive: `CREATE TABLE foo (...)` flagged `foo` as an unknown table because the target name was run through the same existing-table resolution as a `SELECT ... FROM foo`. The fix adds `_created_table_name`, which returns the target only for `CREATE TABLE`/`VIEW` (unwrapping the `exp.Schema` wrapper for the `(...)` form and reading the `exp.Table` directly for the `AS SELECT` form), and folds that single name into the local scope so neither it nor its freshly-declared columns are checked against the base schema.

Only the created name is added to `local_scope_names`, so:

```
CREATE TABLE widgets (id, name)        -> widgets local; declared cols not checked      (clean)
CREATE TABLE t2 AS SELECT id FROM users    -> t2 local; users validated as a real source (clean)
CREATE TABLE t3 AS SELECT id FROM customers -> t3 local; customers flagged unknown        (error)
CREATE INDEX idx ON customers (...)    -> kind is INDEX, not TABLE/VIEW; customers flagged (error)
INSERT INTO customers (id) VALUES (1)  -> no CREATE carve-out; customers flagged           (error)
```

The declared-columns case is safe for a subtle reason worth recording: for a bare `CREATE TABLE`, the created name is not a *real* table (absent from `table_columns`), so `real_tables_in_query` is empty and the unqualified-column branch never fires. CTAS source tables remain in `real_tables_in_query` and are validated normally. CREATE INDEX is correctly excluded from the carve-out because its `kind` is not TABLE/VIEW, so its `ON` target is still resolved against the schema. Five new tests pin each row of the table above.

### Documentation and operability items

Postgres-only live-DB support (#2) is now explicit rather than implicit: the README's "Known limitations" section states that syntax validation spans all dialects but connection testing, schema introspection, and sampling are Postgres-only, and the SPA renders a note when a non-Postgres dialect is selected. This matches the actual `create_adapter` behavior (other dialects raise `NotImplementedError`) and closes the gap between the dialect dropdown and reality without over-promising.

The localhost CORS default (#3) is unchanged in value but now carries a production-critical warning in `.env.example` and a `cors_is_localhost_default` startup check that logs a WARNING when the default is left in place. The stale optimize docstring (#4) is a one-line correction and now describes the implemented AI re-validation path.
